## ADDED Requirements

### Requirement: 员工与长期 Agent 一一关联

每个数字员工 MUST 是具有独立身份和职责的长期责任主体，并与一个独立的真实 AgentScope Agent 稳定关联，不依赖岗位模板。创建和编辑 SHALL 支持名称、领域、职责、工作指令与头像等员工字段；职责和指令保存后 MUST 更新原生实际执行指令，姓名 MUST 与原生 Agent 姓名一致。

#### Scenario: 创建独立员工
- **WHEN** 用户提交有效的员工名称、职责和工作指令
- **THEN** Nexus 创建实际原生 Agent，保存其顶层标识与员工扩展的唯一关联，返回真实创建结果

#### Scenario: 修改员工配置
- **WHEN** 用户保存员工名称、职责或工作指令的修改
- **THEN** 原生 Agent 的相关配置真实更新，员工详情反映已保存值，新建对话使用更新后的实际执行指令

### Requirement: 真实员工列表和详情

系统 SHALL 提供员工列表、按名称搜索、详情和配置展示，展示实际保存的身份、职责、工作指令、启用状态和能力关联。不存在的员工和资源 SHALL 显示空状态；读取失败 MUST 显示失败，不以演示员工或模拟配置填充。

#### Scenario: 搜索和查看员工
- **WHEN** 用户按员工名称搜索并打开匹配员工详情
- **THEN** 列表返回真实匹配记录，详情中的身份、职责、启用状态和能力与服务端保存值一致

#### Scenario: 无记录或读取失败
- **WHEN** 尚无员工、搜索没有匹配项，或者服务端读取失败
- **THEN** 页面分别展示空状态或错误状态，不生成虚构员工记录

### Requirement: 启停在实际运行前生效

员工启用状态 MUST 持久保存并由服务端执行约束。禁用员工后，私聊、讨论输入和员工间消息均 SHALL 不触发该员工的新运行；已排队的触发在实际启动前 MUST 再检查启用状态。启停 SHALL 不依赖浏览器按钮状态实现。

#### Scenario: 禁用后阻止所有新触发
- **WHEN** 员工禁用后收到私聊发送、讨论 @ 或员工间投递请求
- **THEN** 服务端拒绝新的推理触发并返回明确原因，即使请求绕过页面也不能启动该员工

#### Scenario: 排队期间被禁用
- **WHEN** 某次触发已排队但尚未开始，员工随后被禁用
- **THEN** 触发在实际执行前被拒绝，不因入队时曾启用而继续启动

#### Scenario: 重新启用
- **WHEN** 用户重新启用未删除员工并刷新页面或重启服务
- **THEN** 启用状态保持一致，该员工可以接受后续有效触发，既有历史保留

### Requirement: 原生资源选择和真实能力绑定

Knowledge、Skill 和 MCP Tools SHALL 从 AgentScope 的真实资源目录选择，并以稳定资源标识保存员工的默认关联，不通过自由输入或假目录重复定义资源。新建 Session 时 MUST 落实所选能力，实际暴露的工具 MUST 受明确允许目录约束，不默认开放所有宿主或版本外工具。缺少配置、资源失效或关联失败 SHALL 明确报错。

#### Scenario: 选中资源在新会话生效
- **WHEN** 用户从真实目录选择可用 Knowledge、Skill 或 Tools 并成功保存，然后新建该员工会话
- **THEN** 新 Session 真实关联所选资源，员工能够使用被允许且实际可用的能力，详情展示与关联结果一致

#### Scenario: 目录为空
- **WHEN** 官方资源目录没有可选择条目
- **THEN** 选择器展示空状态，不补演示资源，也不以自由输入标签冒充已配置能力

#### Scenario: 资源失效或绑定失败
- **WHEN** 已选资源被移除、缺少必要配置，或者创建 Session 时原生能力关联失败
- **THEN** 操作明确报告相应限制或失败，不把只有本地标签的会话作为能力配置成功的会话返回

### Requirement: 删除前归档并真实删除 Agent

删除员工 MUST 先冻结新运行及待投递、中断该员工的当前运行，并等待已受理运行实际退出、最终历史持久化完成，完整导出其原生历史和附件引用为永久不可执行的只读归档，再调用真实原生 Agent 删除接口。中断请求被受理或收到终态事件 SHALL 不单独视为落盘完成。归档失败或等待超时 MUST 禁止原生删除；原生删除失败 SHALL 保留可重试删除状态并继续禁止新运行。成功后员工 SHALL 从可运行列表和讨论成员中移除，不能以仅本地软删除冒充原生删除。

#### Scenario: 删除成功并保留只读历史
- **WHEN** 员工存在私聊、讨论历史和附件引用，且归档与原生删除均成功
- **THEN** 原生 Agent 确实不存在，已删除员工不能继续运行且退出讨论成员，原匿名所有者仍可从历史入口查看只读消息和访问其有权查看的归档附件

#### Scenario: 归档失败
- **WHEN** 删除前无法完整导出该员工的原生历史或附件引用
- **THEN** 不调用原生删除接口，报告失败原因并允许重试，不丢弃原生历史

#### Scenario: 原生删除失败
- **WHEN** 归档已完成但原生删除接口失败
- **THEN** 不报告删除成功，员工保持禁止新运行的可重试删除状态，重试不破坏已完成归档

#### Scenario: 中断后的尾部内容仍在保存
- **WHEN** 中断已受理但原生最后输出尚未持久化
- **THEN** 系统等待运行真正退出再归档，归档包含最终可保存内容；超时明确失败且不删除原生 Agent

#### Scenario: 原生删除成功但本地确认失败
- **WHEN** 原生 Agent 已被删除，而本地删除结果尚未成功确认
- **THEN** 重试依据已完成归档与稳定原生标识核实删除结果，不重建 Agent、不丢历史，也不恢复员工运行

### Requirement: 跨服务写入不伪造成功

员工创建、编辑、启停、资源关联和删除 SHALL 由服务端提供明确结果。涉及原生写入的操作 MUST 依据实际原生结果返回成功、失败或可重试状态；本地扩展和关联 SHALL 不掩盖上游失败，也不留下被展示为正常可运行员工的未完成关联。

#### Scenario: 创建或编辑上游失败
- **WHEN** 本地请求已收到，但原生 Agent 创建或修改失败
- **THEN** 用户看到明确失败或待重试状态，页面不提前显示保存成功，后续读取不把未完成变更当作已生效配置

#### Scenario: 原生写入成功而本地保存失败
- **WHEN** 原生 Agent 写入已成功，但员工扩展或关联未能成功保存
- **THEN** 系统明确报告未完成状态并允许修复或重试，不返回正常成功结果，也不把该未完成关联用于新的员工运行
