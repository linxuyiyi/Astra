## 为什么

Agent Worker 维护记录里的请求人目前由浏览器默认写死为 `console-admin`，后端请求模型也接受并直接保存请求体里的任意文本。页面显示的既不是当前用户，也无法追溯到实际操作者；重试、取消和只读核对同样没有记录是谁发起的。身份解析链路已经存在（可信代理头、手动 UID 与 `nexus_uid` Cookie），维护 API 只是没有接入。

## 变更范围

- 提交、取消、重试、只读核对维护操作时，请求人由服务端从可信身份解析，不由请求体决定。
- 维护记录继续保存原始发起人；取消、重试与核对把实际操作者写入对应维护事件，不覆盖发起人。
- Worker 维护页显示真实请求人；历史 `console-admin` / `api` 记录标注为未记录 UID，不追填当前用户。

## 非目标

- 不改维护操作状态机、租约、占用保护与执行器。
- 不改 Runtime 生命周期、Task 状态或 Worker 调度判定。
- 不新增用户表、角色或权限模型；只复用现有 UID 解析链路。
- 不重建历史记录，不为缺失 UID 猜测归属。

## 影响

- `POST /api/agent-workers/{id}/maintenance` 请求体只保留 `action`；请求体里的 `requested_by` 被忽略。
- 取消、重试、核对接口新增身份要求；缺少身份返回 401，与现有 `require_owner` 一致。
- 无数据库迁移；审计信息写现有维护事件表。
- 前端维护页展示与历史标注随之调整，展示裁剪一并实施，但不改变维护语义。
